## Overview

The `@Access` decorator sets how the API reads and writes a field. A field is read-only, write-only or read-write. An override can give one action (`get`, `list`, `new` or `edit`) a different mode.

## Separate field policy from caller permissions

`@Access` answers "may this action read or write this field?". It does not answer "may this user access this record?". Authenticate the caller and apply record-level policy separately. A write-only password stays out of responses, but `@Access` does not hash it.

Build the field policy in this order.

1. Set `@Access` on each public field. A field without it stays private.
2. Add action overrides where creation and editing differ.
3. Add `@Listable` to the fields list responses select. Read access alone does not put a field in a list response.
4. Add validators and mandatory-field rules for writable inputs.

For example, a display name is readable and writable, an ID is read-only, and a password is write-only. Test each direction. The routes ignore a value sent for a read-only field. A missing mandatory field is a validation error, covered on the [validators page](./5.validators.md).

## Access modes

The `AccessMode` enum defines three modes.

```typescript
import { Access, AccessMode } from "@antelopejs/interface-data-api/metadata";
```

| Mode                   | Value | Description                                                                                            |
| ---------------------- | ----- | ------------------------------------------------------------------------------------------------------ |
| `AccessMode.ReadOnly`  | `1`   | The field is readable. A list response also needs the pluck mode to select it. POST and PUT ignore it. |
| `AccessMode.WriteOnly` | `2`   | POST and PUT bodies accept the field, and no response holds it                                         |
| `AccessMode.ReadWrite` | `3`   | The field is readable and writable                                                                     |

## Basic usage

### Read-only fields

A read-only field appears in responses, and create and update requests cannot change it. The routes ignore a value sent for it in a request body and report nothing.

```typescript fragment
@RegisterDataController()
class UserAPI extends DataController(
  User,
  DefaultRoutes.All,
  Controller("/users"),
) {
  @ModelReference()
  @Model(UserModel, "my-database")
  declare userModel: UserModel;

  @Access(AccessMode.ReadOnly)
  declare _id: string;

  @Access(AccessMode.ReadOnly)
  declare createdAt: string;

  @Access(AccessMode.ReadWrite)
  declare name: string;
}
```

A PUT request to `/users/edit?id=user-123` with `{ "createdAt": "2025-01-01", "name": "Alice" }` updates only `name`. The route ignores `createdAt`.

### Write-only fields

A write-only field accepts input on create and update, and no response holds it. Passwords and other secrets use this mode.

```typescript fragment
@RegisterDataController()
class UserAPI extends DataController(
  User,
  DefaultRoutes.All,
  Controller("/users"),
) {
  @ModelReference()
  @Model(UserModel, "my-database")
  declare userModel: UserModel;

  @Access(AccessMode.ReadWrite)
  declare name: string;

  @Access(AccessMode.ReadWrite)
  declare email: string;

  @Access(AccessMode.WriteOnly)
  declare password: string;
}
```

A GET request to `/users/get?id=user-123` returns `name` and `email`, and never `password`.

```json
{
  "name": "Bob",
  "email": "bob@example.com"
}
```

### Read-write fields

A read-write field appears in responses and accepts input in request bodies.

```typescript fragment
@Access(AccessMode.ReadWrite)
declare email: string;

@Access(AccessMode.ReadWrite)
declare name: string;
```

## Per-action overrides

`@Access` takes an optional second argument that overrides the mode for named actions.

```typescript fragment
@Access(mode: AccessMode, overrides?: Record<string, AccessMode>)
```

The `overrides` object maps action names (`"get"`, `"list"`, `"new"` and `"edit"`) to an `AccessMode`. An action that `overrides` does not name uses `mode`.

To read the mode a field has in one action outside the routes (to render a form read-only on edit, for example), call `GetEffectiveMode(field, action)` from `@antelopejs/interface-data-api/metadata` with the field's metadata (`meta.fields[name]`). It returns the mode the routes apply.

### Example: writable on create, read-only on edit

```typescript fragment
@RegisterDataController()
class UserAPI extends DataController(
  User,
  DefaultRoutes.All,
  Controller("/users"),
) {
  @ModelReference()
  @Model(UserModel, "my-database")
  declare userModel: UserModel;

  @Access(AccessMode.ReadOnly)
  declare _id: string;

  @Access(AccessMode.ReadWrite)
  declare name: string;

  // Writable on new, read-only on edit
  @Access(AccessMode.ReadWrite, { edit: AccessMode.ReadOnly })
  declare role: string;

  // Read-only, except on new
  @Access(AccessMode.ReadOnly, { new: AccessMode.ReadWrite })
  declare age: number;
}
```

With this configuration:

- `role` is readable and writable in every action except `edit`, where it is read-only.
- `age` is read-only, except in `new`, where a create request can set it.

## Fields without `@Access`

An ordinary field needs `@Access` to appear in responses or accept input. `@Listable` alone grants no access. The derived-field decorators [`@Joined`](./10.joined.md) and [`@Computed`](./11.computed.md) are the exceptions. They set read-only access themselves.
